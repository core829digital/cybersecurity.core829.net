// 04 — Cosa trova

Le falle che contano.
Quelle che un attaccante usa davvero.

Copriamo l'OWASP Top 10 e oltre: anche gli errori di logica specifici della tua attività, che nessuno scanner automatico è in grado di capire.

ACCESSI

Controllo degli accessi

Dati di altri utenti raggiungibili cambiando un numero nell'indirizzo, privilegi da amministratore ottenuti senza averli, login aggirabile.

INIEZIONI

Iniezioni

SQL e NoSQL, comandi di sistema, template lato server: input che il sito esegue invece di trattare come semplice testo.

SERVER

Lato server

SSRF, XXE, deserializzazione insicura ed esecuzione di codice remoto: le falle che aprono le porte dell'infrastruttura.

CLIENT

Lato browser

XSS memorizzato, riflesso e DOM, CSRF, prototype pollution: attacchi che colpiscono i tuoi clienti attraverso il tuo sito.

LOGICA

Logica di business

Prezzi modificabili nel carrello, coupon riutilizzabili, passaggi obbligatori saltati, race condition sui pagamenti.

SESSIONI

Autenticazione e sessioni

Token JWT manipolabili, sessioni che non scadono, protezioni deboli contro il furto di credenziali.

API

API

Endpoint senza autenticazione, campi che l'utente non dovrebbe poter modificare, limiti di frequenza aggirabili.

CONFIG

Configurazioni e cloud

Servizi esposti per errore, pannelli di amministrazione raggiungibili, header di sicurezza mancanti, componenti obsoleti.

CRITICA · CVSS 9.1VULN-003

Il prezzo del carrello si può modificare dal browser

Il server accetta il prezzo inviato dal browser invece di ricalcolarlo. Chiunque può acquistare qualsiasi prodotto a 0,01 €.

Prova di sfruttamento

POST /api/carrello/conferma
{ "prodotto": 4471, "quantita": 1, "prezzo": 0.01 }

→ 200 OK · ordine #10582 creato a 0,01 €

Correzione

Ricalcolare sempre prezzo e totale sul server partendo dal catalogo, ignorando i valori inviati dal client.

// 06 — Regole d'ingaggio

Hacker sì.
Fuorilegge mai.

  • Autorizzazione scritta, sempre. Nessun test parte senza la lettera di incarico firmata dal titolare del sistema.
  • Dominio verificato. Prima di iniziare controlliamo che il sito sia tuo, con un record DNS o un file sul server.
  • Perimetro e orari concordati. Testiamo solo ciò che è nell'incarico, nelle finestre orarie che scegli tu.
  • Test non distruttivi. Niente cancellazione di dati e niente attacchi di saturazione che possano fermare il servizio.
  • Massima riservatezza. Accordo di riservatezza, report consegnati in modo cifrato, dati conservati in UE.
  • Utile per GDPR e NIS2. L'art. 32 del GDPR chiede di testare regolarmente l'efficacia delle misure di sicurezza: il report lo documenta.

// 09 — Domande frequenti

Le risposte,
prima di chiedere.

Non trovi quello che cerchi? Scrivici a hello@core829.net.

È legale attaccare un sito?

Sì, se c'è l'autorizzazione del titolare. Per questo ogni test parte solo dopo la firma della lettera di incarico, che stabilisce cosa possiamo testare, quando e con quali limiti, e dopo aver verificato che il dominio sia tuo. Senza autorizzazione non lavoriamo.

Il test può bloccare o danneggiare il mio sito?

I test sono non distruttivi: non cancelliamo dati e non facciamo attacchi di saturazione. Lavoriamo nelle finestre orarie che scegli tu e possiamo escludere le parti più delicate. Per i sistemi critici consigliamo di testare un ambiente di prova identico a quello reale.

Che differenza c'è con uno scanner automatico?

Uno scanner segnala ciò che potrebbe essere un problema, con molti falsi allarmi. Gli agenti invece provano a sfruttare davvero ogni falla e la riportano solo se ci riescono, con la prova. In più ragionano sulla logica del tuo sito, per esempio su come funzionano carrello, ruoli e permessi.

Sostituisce un penetration test manuale?

Per la maggior parte di siti, e-commerce e web app offre una copertura ampia, in tempi e a costi molto più bassi. Ogni risultato è rivisto dal team CORE829. Per sistemi ad altissimo rischio possiamo affiancare verifiche manuali mirate: lo valutiamo insieme nel preventivo.

Cosa serve da parte mia?

L'indirizzo del sistema, la firma dell'autorizzazione e un referente tecnico. Per i test con login ci servono utenti di prova. Per la revisione del codice, l'accesso in lettura al repository.

Quanto tempo ci vuole?

Dipende dal perimetro. Un check-up si chiude in genere in pochi giorni dalla firma; un test completo su una web app richiede di più. I tempi esatti sono indicati nel preventivo.

Che fine fanno le informazioni sulle vulnerabilità?

Sono riservate: le condividiamo solo con i referenti indicati da te, con consegna cifrata e accordo di riservatezza. I dati restano su server in UE e vengono cancellati al termine del periodo concordato.
